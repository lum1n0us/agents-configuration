# 中英混排技术写作规则

**适用**：所有中文产出——对话回答、工具描述、错误信息、状态汇报、PR/issue 正文、设计文档、给其他 agent 的提示词。
**目标形态**：**中英混排，不是妥协**。中文承载叙述与语法，英文承载英文更擅长的部分。不追求全中文。
**不适用**：创意文案、营销文案，以及任何需要语气和说服力的文本。

**来源**：从 [asd-ste100](https://github.com/danyuchn/asd-ste100-skill)（ASD-STE100 的 agent 版）中筛出可迁移到中文的部分，并改造了度量与形态。英语专属规则已剔除，见第三节。

---

## 语言选择：中英混排

中文承载语法与叙述，英文保留它既有的形态。判断标准只有一条：**生态里怎么叫，就怎么叫。**

### 保留英文的四类

| 类别 | 例子 |
|---|---|
| 专业术语 | commit、rebase、race condition、backpressure、idempotent、sharding |
| 产品 / 库 / API / 命令名 | React、pnpm、`git rebase`、`Content-Type`、`ctx.skills` |
| 社区惯用写法与俗语 | LGTM、nit、WIP、ship it、footgun、yak shaving |
| 缩写 | RTO、FTUE、LCP —— **首次出现时展开一次**，之后直接用缩写 |

### 不要做两件事

**1. 生造或硬译译名。** 社区通用的是英文原词，就不要再造一个中文对应物。典型反例：race condition 写成「竞态条件」、backpressure 写成「背压」——读者对齐术语时反而要多做一次翻译。

**2. 中英夹生：把英文词按中文语法变形。**

- ✗ 这个 request 的 timeout 被 exceed 了。
- ✓ 这个 request 超时了。/ This request timed out.
- ✗ 我们需要 general 一下这个 case。
- ✓ 这个 case 需要泛化。

### 一致性的落点

一经选定，全文统一形态。不要在「race condition」和「竞态条件」之间来回切换——那正是第 1 条要禁止的近义词轮换，只是发生在语言之间。

## 一、通用规则（与语言无关，直接适用）

### 1. 一物一名

同一事物或动作，全文只用同一个**形态**——中文或英文都行，但只能选一个。

- ✗ 用户提交请求后，客户端会收到回执，**访客**可以在界面看到结果。
- ✓ 用户提交请求后，客户端会收到回执，**用户**可以在界面看到结果。
- ✗ 偶发的 race condition 会导致数据错乱，出现竞态条件时……
- ✓ 偶发的 race condition 会导致数据错乱，出现 race condition 时……

不混用：检查 / 校验 / 确认；删除 / 移除 / 清理；配置 / 设置 / 选项。

选哪一个由「语言选择」一节决定：生态通用英文，就保留英文。

### 2. 一句一意

不把多个意思塞进一句。

- ✗ 打开配置文件，把超时改成 30 秒，然后重启服务并确认日志无报错。
- ✓ 打开配置文件。把超时改成 30 秒。重启服务。确认日志无报错。

### 3. 动词优先，不名词化

动作就用动词。

| ✗ | ✓ |
|---|---|
| 对日志进行分析 | 分析日志 |
| 提供帮助 | 帮助 |
| 进行优化处理 | 优化 |
| 做出调整 | 调整 |

### 4. 保真（最重要的一条）

- **不把情态写成事实**：「可能已失败」不得改成「失败」；「或许由 X 引起」不得改成「X 是原因」。
- **不加原文没有的内容**：事实、频率、因果、机制，一个都不加。
- **不丢限定条件**：范围、例外、安全前提、数字。宁可保留长句，也不要静默简化。
- 如果为了让意思不变而必须保留较长表达，按第七节的输出契约单独标注。

### 5. 结构

- 一段一个主题。
- 3 个及以上步骤或条件，用编号或项目列表，不要埋进一句话。

### 6. 不用营销形容词

无缝、强大、极致、前沿、流畅、丝滑、开箱即用。

要么删掉，要么换成支撑这个说法的具体数字。

### 7. 输出契约

当任务是**改写 / 润色 / 写文档**时：

- 默认**只给正文**。不加前言、不加「本次修改说明」、不加违规数量、不加「如需进一步优化请告诉我」。
- 唯一允许的附加：如果为保真而故意保留了较长的表达，在正文后单独一行，以 `保留原样:` 开头，写明保留了什么、否则会丢什么。
- 用户明确要求时才输出对照表（「给我看 diff」「违反了哪些规则」）：三列 `违反的规则 | 原文 | 改写后`，末尾一行 `模式：严格。共 N 处。`，再加一行说明你**故意没有**改的地方及原因。

## 二、需改造后适用

### 句子长度（软上限，按字数）

中文没有稳定的「词」边界，字数与信息量也不等比，所以用字数而不是词数：

| 文本类型 | 上限 |
|---|---|
| 指令、步骤、错误信息 | ≤ 30 字 |
| 描述性文字 | ≤ 45 字 |
| 排除项 | 代码、路径、命令、错误串、专有名词、原文引用 |

这是**软约束**。不要为了凑字数删掉必要的限定条件——那违反第 4 条。

### 中文特有的「万能动词 + 抽象名词」

英语的短语动词（take off / spin up）在中文的对应毛病，同样让读者无法判断具体动作：

| ✗ | ✓ |
|---|---|
| 对配置进行处理 | 修改配置 |
| 加以解决 | 解决 |
| 做出调整 | 调整 |
| 实现优化 | 优化 |

### 省略主语

英语 STE 要求主语显式，但中文省略主语常常更自然。改为：

- 读者能无歧义地判断施动者时，省略即可。
- **只有会产生歧义时**，才必须补出主语。

### 主动语态（降级为可选）

中文被动（被 / 由 / 受到 / 得到）有标记且合法，不必强求全主动。只在两种情况下改：

- 施动者不重要却被写出来：「文件被系统删除」→「文件已删除」。
- 被动掩盖了读者需要的责任归属。

## 三、以下英语专属规则不适用于中文（不要套用）

| 英语规则 | 为什么不可用 |
|---|---|
| 官方 ~900 词 approved 词典 | 英语词表 |
| 一词性（one part of speech per word） | 依赖词典裁定词性；中文兼类词没有这个裁定 |
| 禁短语动词（Rule 9.3） | 英语构式 |
| 简单时态（禁现在完成时、禁 -ing 作动词） | 中文无时态屈折，靠「了/过/着」等体标记 |
| 冠词显式 | 中文无冠词 |
| 禁分号（Rule 8.1） | 英文标点规范；中文分号合法且有用 |
| 名词堆叠 ≤ 3 词 | 度量不适用（若需要，改用「定语层数」软约束） |
| scripts/ste-lint.py | 检查的是英语规则，对中文不产生有效输出 |

## 四、改写流程

1. 先通读原文，弄明白它**必须保留**什么，再动手。
2. 逐句标出违反第一、二节规则的地方，尤其注意第 4 条的情态与限定条件。
3. 重写句子，同时保证意思**完全不变**。
4. 自查三问：情态动了吗？条件丢了吗？加了原文没有的事实吗？
5. 按第 7 条的输出契约交付。
6. 原文本来就合格，就说合格——不要硬改。
